# 流体の決定論 — AI が «見て直す» を回せる .fluid

AI にエフェクトを作らせるとき、効いているのはループの速さではなく **同じ入力から同じ絵が出ること** だ。
「値を変える → 絵を見る → 直す」の輪は、見た絵と焼けた絵が同じでなければ回らない。
このメモは 2026-09-14 に入れた変更 (刻みの統一・指紋・ソルバーの明示・出力名の固定) の理由と契約を残す。

---

## 1. 何が壊れていたか

流体のソルバー自体は最初から決定論的だった。乱数は `recipe.seed` から引くハッシュだけで、
時刻にもスレッド数にも依存しない (`FluidSolverTests.SameSeedGivesTheSameResult`)。

壊れていたのは **経路の間** だった。warmup の進め方が 3 通りに割れていた:

| 経路 | warmup の進め方 |
|------|----------------|
| 2D の焼き (`FluidBaker`) | コマ幅で 1 刻み。**substeps を掛けない** |
| 3D の CPU (`VolumeFlipbookFluid`) | 同上 |
| 2D のプレビュー (`FluidBakeService` / `FluidPreviewCache`) | 通常のコマと同じく substeps で分割 |
| 3D の GPU (`FluidGpuSolver`) | warmup をコマ数へ丸め、通常のコマとして進める |

`substeps` は既定 2・プリセットは 3〜4、`warmup` は 0.8〜1.5 秒 (= 30〜50 コマぶん) なので、
**どのレシピでもプレビューと焼きは別のシミュレーションになっていた**。似てはいるが乱流の形が違う。
AI が絵を見て `fluid.set` で直しても、直した先が別物なら意味がない。

同じ性質の穴が他にもあった:

- プレビューは秒で指定していたため、コマ境界に乗らない «焼いたどのコマでもない絵» を見ていた
- 焼きだけ超解像 (`supersampling`) が掛かり、プレビューより滑らかだった
- `bake.solver = "gpu"` は GPU が使えないと黙って CPU へ落ちていた (環境で絵が変わる)
- 3D の出力名が `FindAvailableBase` で `_001` に逃げ、焼き直すたびに別ファイルが増えた
- 「変えた値が効いたか」を判定する手段が、画像を見比べること以外に無かった

---

## 2. 決めたこと

### 2.1 刻みの正本は `FluidStepping.hpp` ひとつ

```
FluidStepPlan { frameDt, substeps, warmupFrames, frameCount, loopOverlap }
```

**warmup も «普通のコマ» として解く**。端数は切り上げてコマ数に丸める (`FluidWarmupFrames`)。
こうすると「焼きの第 n コマ」= 「warmupFrames + n コマ進めた状態」で、4 つのソルバー経路すべてで一致する。
値域のクランプ (`NormalizeFluidOutput`) もここが持つ。経路ごとに別々にクランプすると、境目の値で刻みがずれる。

### 2.2 プレビューは焼きと同じ入口を通る

`RenderFluidBakeFrames(recipe, frames, size, out)` が唯一のコマ生成器で、`BakeFluid` もプレビューもこれを呼ぶ。
超解像もループのクロスフェード (先頭 `loopOverlap` コマを «末尾の続き» と混ぜる) も、この中で焼きと同じ規則で再現される。

結果、**`fluid_preview(frame = n)` の絵は `fluid_bake` の n コマ目と 1 画素まで同じ**。
これは `FluidDeterminismTests` が縛っている (ループ時・超解像ありも含む)。

プレビューの指定はコマ番号が第一級になった。秒 (`time`) は互換として残し、一番近いコマへ吸着させる。

### 2.3 指紋 — 変化の有無を 1 回の文字列比較で

`BakeFingerprint` (FNV-1a 64 → 16 桁 hex) が焼いた画素から指紋を作り、
`FluidJobStatus.fingerprint` として AI に返る。前回と同じなら絵は 1 画素も変わっていない。
「効かない値をいじり続ける」を機械的に検出できる。

指紋は **人が見る絵** (色 + MV) から取る。`.vfield` は絵に出ないので混ぜない。

### 2.4 ソルバーは明示でき、落ちたら必ず言う

`[bake] solver` は 3 値になった:

- `auto` (既定) … GPU で解き、使えなければ CPU へ落とす。理由は `fallbackReason` に載る
- `gpu` … GPU で解けなければ **焼かない**。環境によらず同じ絵が要るときはこちら
- `cpu` … 常に CPU (96³ まで)

どれで解いたかは `solverUsed` に出る。プレビューも同じ規則で、`gpu` 指定なら CPU の絵を見せない
(「見えたのに焼けない」を作らない)。

### 2.5 出力名は固定

`.fluid` から焼く経路は必ず同じ名前へ上書きする (`overwriteOutputs`)。
空きを探して `_001` を足すのは、人が «前のを残して焼き比べたい» と言ったときだけ。

### 2.6 `.fluid` はバイト列まで安定

`float` は最短往復の 10 進で書く (`0.1f` が `0.10000000149011612` にならない)。
読んで書き戻しただけで行が動かないので、AI が 1 項目直した差分に無関係な行が混ざらない。

### 2.7 ばらつきは乱数ではなく seed の列挙で

`fluid_preview(variants = N)` は seed を 1 つずつずらした N 通りを 1 枚に並べる。
気に入った 1 枚の seed を `fluid_set` で固定すれば、その絵が何度でも焼ける。
「振り直したら別のものが出た」を最初から選択肢に入れない。

`contactSheet = true` は全コマを焼いたアトラスの並びで 1 枚にする。時間方向の当たり外れが 1 往復で見える。

### 2.8 書き込みの衝突で黙って消さない

`FluidDocument::Save` は書く直前にディスクの更新時刻を見直し、外 (AI・Baker) が書いていれば書かずに衝突を立てる。
自動保存もここを通るので、3 秒の無操作が他人の書き込みを飲み込むことはない。
逆に AI が書くときは、人が未保存で開いていれば `warnings` でそう言う。

---

## 3. 契約の範囲

決定論を約束するのは **同じバイナリ・同じ環境で** という条件つき。
GPU で解いた結果はドライバやベンダーが変われば変わりうるので、テストで固定するのは CPU 経路だけにしてある。
CI で絵を縛るときも CPU 経路を使うこと。

---

## 4. 触るときに壊しやすいところ

- **warmup を «秒» のまま刻みたくなる**。コマ数へ丸める理由は経路間の一致で、精度ではない
- **プレビュー用の軽い経路を別に書きたくなる**。それをやると 2026-09-14 以前へ戻る。
  解像度を落とすのは良い (`FluidPreviewCache` の編集中プレビューはそうしている) が、**刻みは変えない**
- **指紋に «絵に出ないもの» を混ぜたくなる**。混ぜると「絵は同じなのに指紋が違う」が起き、判定が嘘になる
- 新しいソルバー経路を足すときは `FluidStepping` を通すこと。通さない経路が 1 つあれば、それが次のずれになる
