# ランタイム最適化仕様

[FBZZ Engine 内部仕様](engine-internal-spec.md) の性能編。対象は現行 DX12 / C# SDK の作業ツリー。個別機能の契約はリンク先を正本とする。この文書では、何の作業を省くか、何が残るか、どの条件で速度を判定するかをそろえる。

## 性能の目標と優先順位

60 FPS は約 16.67 ms、120 FPS は約 8.33 ms のフレーム間隔に相当する。120 FPS を目標とする場面では 8.33 ms を比較の目安にする。対象シーン・解像度・品質・実行モード・ハードウェアを決めてから、全体のフレーム時間に加えて CPU、GPU、待ちを測る。CPU と GPU は別フレームを並行して処理できるため、両方の合計をフレーム間隔にしない。

優先順位は、(1) 不要な処理を省く、(2) 変更がない計算と転送を再利用する、(3) 境界の往復と待ちをまとめる、(4) 残ったホットループのデータ配置・SIMD・並列化を検討する、の順を基本とする。例外は実測で説明する。CPU の短縮が GPU 律速のフレーム間隔に出ない場合もあるため、区間の短縮と体感の改善は別々に記録する。

状態の表記は **常用**（対象経路で通常使う）、**条件付き**（資源・互換性・設定などの条件を満たす場合）、**任意**（明示的な有効化が必要）、**候補**（この文書が実装済みとしない）の四つとする。「実装あり」は、全シーンへの適用や高速化の保証を意味しない。

## CPU・データアクセス

| 処理 | 省く作業と残る費用 | 維持する契約・確認点 |
|---|---|---|
| **常用**：型別 Component の走査・一括破棄 | 安定アドレスの型別 chunk を連続走査し、Renderer 候補は密な ID 列で絞る。破棄時は生存順を維持して外側の破棄処理の終了時に所有配列を詰める。対象 Renderer の照合・ID コピーは残る | span の借用中は追加・削除・Clear をしない。Entity 世代・Component 寿命・Scene の順序、`OnDestroy` 中の見え方を維持。[大量個体処理](ecs-bulk-processing.md) |
| **条件付き**：System の並列化 | 競合しない System を Phase 内でまとめる。現在の TaskSystem は共有 FIFO で、batch の終了を待つ。小さい仕事では投入・待機費用が利益を消す | ComponentAccess と依存順が明示された範囲に限定する。`queue wait`、worker 実行、呼び出し側の待ちを分けて確認する。[Scheduler 実装](../../Projects/Engine/src/Core/Scheduler/SystemScheduler.cpp) · [TaskSystem 実装](../../Projects/Engine/src/Core/Concurrency/TaskSystem.cpp) |
| **常用**：作業領域の再利用 | 物理クエリ、階層同期、姿勢評価などで一時領域を使い回す。容量不足や再入時の追加領域、保持するメモリは残る | 呼び出しの深さ、スレッド、Scene をまたいで借用中の領域を上書きしない。通常時だけでなく最大容量と縮退も測る。[Runtime 作業領域](runtime-workset-optimization.md) |
| **常用**：Math のインライン・SIMD | 小関数の呼び出しと対応する算術を短縮する。公開ベクトル型の形を広げず、演算内で SIMD を使う。連続データ化やアルゴリズム改善は別の変更 | 比較では同じ入力・出力要件を使い、未使用成分が消された計測を避ける。丸め、ゼロ長、非有限値、保存や ABI を確認する。[Math SIMD](math-simd.md) |
| **条件付き**：C# のバッチ API・ネイティブ処理 | 大量個体は既存の型付きサービスで managed/native の往復と繰り返しの検索を減らす。値の収集、転送、結果の公開費用は残る | Script callback のスレッド・寿命を守る。呼び出し数、往復数、確保量、実シーンの `Script` / `LateScript` 時間を比較する。言語を変えたことだけで利益を推定しない。[C# 計測](csharp-benchmarks.md) · [Component サービス](csharp-component-services.md) |
| **常用**：Physics BroadPhase の差分更新 | BVH を保持し、変更した葉と祖先を refit。入力の所属が変わるか木が劣化すれば再構築する。全 AABB の照合と候補探索は残る | 現在の衝突フィルターを使い、候補集合と重複なしを維持。不正な境界は安全な全候補判定へ退避。候補順と PGS のビット一致は契約に含めない。[差分 BroadPhase](broadphase-incremental.md) |

CPU のホットループは、**走査回数、読み書きする byte 数、算術命令、待ち時間**を分けて考える。算術よりデータ取得が高い場合は、必要なフィールドだけをまとめて読む、連続した要素を内側のループでたどる、繰り返し参照する作業集合を小さく区切る、といった変更を先に比較する。作業領域を SoA にする場合は、詰め替えと結果の公開を含めて測る。キャッシュに収まる小入力と、収まらない実用規模の両方を使う。

Math は `Vector3` を 12 byte、`Matrix4` を 64 byte のまま扱い、SIMD の型は演算の内部に閉じる。`Vector3` の 16 byte 化は単体ロードが減っても、同じ個体数の配列でデータ量が 1/3 増える。公開型を一律に変える判断材料にはしない。変更候補は、インライン化、データ配置、命令列を分けて比較し、全成分を出力する。同じ入力で値・許容誤差、数値の境界、配列末尾の読み取り、実シーンの差を確認する。ヘッダーに処理を移す場合はビルド時間も別に確認する。[ビルド性能](../conventions/build-performance.md)

## 描画の作業量と同期

| 処理 | 適用条件と削減対象 | 限界・退避条件 |
|---|---|---|
| **常用**：同一フレームの幾何入力共有 | Scene・フレーム・資源・失効条件が一致する場合、複数ビュー間で幾何の準備を共有する | カメラ、光源、選択、可視性などのビュー固有情報を共有扱いしない。現在の材質や公開値が変わった場合は既存の失効・再照合に従う。[抽出作業領域](runtime-workset-optimization.md) |
| **条件付き**：静的 MeshRenderer のフレーム間再利用 | 同じ入力の world 行列、逆転置、world 境界を再利用。変更通知で同フレーム snapshot を失効させる。通知されない直接変更も幾何構築時に照合する | Renderer 候補を照合する費用は O(R)。変更数 K のみを処理する方式ではない。材質、draw command、変形頂点、previous world まで永続化する仕様ではない。全件移動・初期化の費用を測る。[静的 Mesh 再利用](static-mesh-render-reuse.md) |
| **任意**：抽出の revision / fused 経路 | `FBZZ_RENDERER_WORKSET_MODE=revision` は構造世代の確認を使い、`FBZZ_RENDER_EXTRACTION_SCAN_MODE=fused` は色可否の判定を既存走査へ融合。`validate` は比較用 | 未指定・未知値は `legacy`。ID のコピー、現在値の照合、変更時の並べ替えは残り得る。snapshot と Scene の順序を維持し、診断用の `validate` と本番候補を同じ費用として扱わない。[抽出走査](render-extraction-scan-optimization.md) |
| **条件付き**：ビューと光源の可視判定 | ビューの視錐台・距離・レイヤー・LOD を適用。影は光源側の候補を使う。CPU 遮蔽はカメラ単位で **任意、既定無効** | 遮蔽に確実な証拠がない場合（near 交差、未確定な境界、未対応の遮蔽物など）は描画側に残す。CPU 遮蔽の結果を影や Ray Scene の除外に流用しない。視点移動中の欠けと判定自体の時間を確認する。[ビュー別カリング](view-culling.md) · [CPU 遮蔽](occlusion-culling.md) |
| **条件付き**：自動インスタンシング | 同一の mesh、材質・描画状態など、パスが束ねられる不透明描画をまとめ、提出数を減らす | 透過の順序、LOD 遷移、変形・個別の材質などが束の契約を満たさない場合は通常描画。draw call の減少から GPU の短縮を推定せず、束の準備と upload を計上する。[自動インスタンシング](gpu-instancing.md) |
| **常用**：DX12 の bindless 資源参照 | 共有ヒープ上の添字で参照し、draw / dispatch ごとのディスクリプタテーブル組み立てとコピーを削減する | 添字は資源の寿命に従う。テクスチャの差し替えで古い添字を焼き込まず、バインドを省いても状態遷移は維持する。CPU の提出費用と GPU のパス時間は別々に測る。[Bindless](bindless.md) |
| **任意**：GPU 間接描画 / Mesh Shader | `render.geometry_mode` は既定 `cpu`。`indirect` は対象の水面・地形・静的 instance、`mesh` は対象の高密度静的形状・影・地形 GPU 経路を比較する | 資源、材質、能力、可視条件で通常描画へ戻る。GPU 側で減った件数を CPU 側の候補統計で代用しない。初回分割・転送と定常描画を分けて記録する。[GPU 駆動描画](gpu-driven-geometry.md) |
| **条件付き**：スキンド個体の姿勢共有・更新間隔 | 互換な個体の姿勢・パレットを共有し、距離に応じて更新頻度を落とせる。GPU Skinning の需要駆動は `FBZZ_GPU_SKINNING_DEMAND=1` の **任意** 経路 | ゲーム側が読む骨や RootMotion、影、速度、選択など後から必要になる出力を確認。画面外でも別パスが消費する場合は準備が要る。省略した dispatch 数と実時間を別に扱う。[多数個体](skinned-crowds.md) · [GPU 共有姿勢](gpu-shared-pose.md) · [Skinning の需要と所有](gpu-skinning-demand.md) |
| **任意**：多数ライトの重要度サンプリング | Forward+ / Deferred+ で明示的に有効化し、候補を調べたうえで完全な材質・影・Cookie の評価数を予算内に制限する | クラスタの候補作成と再構成も費用に含める。少数灯・多数灯、静止・移動、TAA の有無でノイズや光量を通常評価と比較する。同画質の単純な計算短縮とは分けて記録する。[多数ライト](many-light-sampling.md) |
| **常用**：RenderGraph と Render Thread | 同じグラフ構成では依存解決・パス除外・寿命解析の計画を再利用。所有済み入力を提出し、CPU 更新と描画命令の記録を重ねる | Graph の寿命解析は物理 heap の aliasing と別。描画スレッドの処理完了は GPU fence の完了ではない。提出枠の上限、命令順、資源退役を維持する。Async Compute は **任意、既定無効** で、キュー間の依存と実際の重なりを確認する。[RenderGraph](render-graph.md) · [Render Thread](render-thread.md) · [Async Compute](async-compute.md) |

同じ形状データでも、**Scene 所属の索引 → 幾何計算の再利用 → ビュー別可視性 → GPU 提出** は別の処理である。例えば `GeometryBuild` が短くても、材質の準備、キュー作成、upload、draw、Present は残る。効果を報告するときは、このうち省いた段階と測った区間を明示する。

## 広域ワールドとメモリ

| 処理 | 予算と公開境界 | 観測するもの |
|---|---|---|
| **条件付き**：非同期アセット | CPU の読み込み・解析、GPU への転送、利用可能な状態の公開を分離する。部分常駐や LRU の効果は接続された呼び出し元と設定に依存する。常駐予算による LRU は既定で無効 | 冷起動、ready までの時間、公開・転送に費やすフレーム時間、常駐・ピーク量、再読み込み数。未計測の確保・VRAM は 0 にしない。[ストリーミング](asset-streaming.md) |
| **条件付き**：World Partition / PCG / HLOD | PCG は Editor で生成し、共通セルの近景と遠景代理を別にベイクする。ランタイムでは worker が読み込み・検証し、Scene への適用はメイン側で行う。対象は設定済みのセルとベイク対象 | 移動、境界の往復、teleport、失敗・再試行で、近景の欠け、二重描画、公開待ち、切り替えのピークを確認する。アセット常駐量、セル数、要求・公開時間、HLOD の画質を別々に測る。[セルと HLOD](world-partition-pcg.md) |
| **常用**：描画資源の寿命と再利用 | フレーム領域、アセット利用権、ResourceManager の寿命 ID / Reset 世代を分ける。保持容量や、旧資源が退役するまで新旧が重なるメモリを含めて判断する | 上限、超過時の挙動、再作成、資源所有者の切り替えを確認する。借用中の資源や受付済み命令を、空き容量を得るために早く解放しない。[モジュールと資源の所有](engine-module-boundaries.md) |

個体 LOD は一つのオブジェクトの詳細度、HLOD はセルなど複数の要素をまとめた遠景の表現。常駐セル数、描画候補数、GPU の描画量は別の指標として記録する。水・地形・植生を同時に含む場面では、単体シーンの値を足す代わりに、同じ移動経路で全体を測って共有資源や重なりを確認する。

### 負荷の大きい場面の切り分け

| 場面 | 比較する区間・作業量 | 維持する見た目・挙動 |
|---|---|---|
| 魚群など多数のスキンド個体 | 個体数と使用クリップ数を分けて増やし、Script / `LateScript`、姿勢評価・パレット転送、GPU Skinning、色・影の各区間を採る。個別の managed/native 往復、骨更新・dispatch 数も別に数える | 近景・遠景・画面外、主画面外でも落ちる影、移動と再表示での姿勢・速度履歴、ゲーム側の骨読み取り |
| 地形・森林 | セルと地形パッチを混同しない。セルの公開費用、パッチの色・影の三角形数、Fiber の近傍生成、Instanced Mesh の候補と提出、色・影の GPU 時間を分ける | 地形パッチ境界と穴、草の根元、遠景樹木の切り替わり、画面外から落ちる影。地形の近傍だけで詳細度を維持する条件は [Instanced Mesh](instanced-mesh.md) と [Fiber](fiber-rendering.md) を参照 |
| 海・湖・水中 | 水面の形状準備と提出、反射・屈折・合成などの GPU パスを分ける。海のみ、湖のみ、併設、水上から水中への移動を同じ解像度で採る。候補や頂点の減少で画素パスの短縮を推定しない | 近景と水平線の波、遠景セルで頂点変位から法線表現に切り替わる境界、水上・水中の見え方。描画 LOD で物理の水面を変えない。[水面の波](water-waves.md) · [水面の物理契約](water-foundation.md) |

## 比較計測の手順

1. **評価条件を先に決める。** 対象のシーン、カメラ経路、期待する削減、同品質か品質変更か、主要な指標と許容する後退を記録する。先に計測して律速区間を確かめる。`fps` の平均だけを採否指標にしない。
2. **基準と候補の条件をそろえる。** コミット・作業ツリー差分、構成と LTO、CPU/GPU・ドライバー・OS、DX12、解像度・品質・シェーダー・機能フラグ、VSync と表示モード、起動引数、シーンとアセット、固定カメラ経路・seed を残す。Edit・Editor Play・Standalone の測定を混ぜない。通常表示と画面外を別ケースとする。
3. **診断と時間比較を分ける。** Profiler、FrameTimeline、PIX で CPU の仕事・待ち・GPU の経路を特定する。正式比較では計測オーバーヘッドを減らし、前後で同じ計測条件を使う。CPU フレームと GPU の取得済み結果は serial・ビュー・世代で対応させ、欠落は別に数える。キャプチャの再生時間を実行時のフレーム時間に置き換えない。[Profiler](profiler.md) · [PIX](pix-profiling.md)
4. **初回と定常を分け、複数回測る。** 初回作成・ロードは専用ケースとし、定常は同じウォームアップ後に同じ区間を採取する。基準と候補を交互に複数プロセスで実行し、順序、各試行の標本数、欠落、集計方法を記録する。P50 / P95 / P99 は計測対象と一緒に記す。短い実行の P99 を過信せず、重要な差は独立再測定する。
5. **実行経路と出力を検証する。** 機能フラグだけで判断せず、対象の経路を通った件数、fallback、描画数・候補数・画像、物理の候補集合などを確認する。同品質は画像・挙動の許容差を事前に決める。LOD、影解像度、更新頻度の変更は品質との交換として別に示す。
6. **採否と適用範囲を決める。** 差が試行間のばらつきに埋もれるなら「改善未確認」。定常の P50 が短くても、初回・P95/P99・メモリ・品質の後退を併記する。速くなる入力を判別できる場合は条件付き採用、利益が確かめられない場合は任意経路または見送りとし、理由を記録する。

| 指標 | 取り方 | 混同しないもの |
|---|---|---|
| フレーム間隔・ホストの経過時間 | 何の開始から終了までか、通常表示か画面外かを明記し、ms の分布で比較する | FPS の平均、CPU ワーカー区間の総和、GPU パスの合計 |
| CPU 区間 | `GeometryBuild`、Script、CPU 記録、packet 受付・完了待ち、`BeginFrame` / `EndFrame` を区別する | 親の Inclusive と子の加算。Script Self は呼び出した Engine API の時間も含む |
| GPU 区間 | 同じ serial・view の有効な timestamp を使い、パス、キュー、実行経路を記録する | 別フレームの CPU 区間、GPU 並行区間の単純合計、未回収 query の 0 ms 扱い |
| 作業量・メモリ | 更新対象数、提出数、転送 bytes、候補／可視件数、常駐・ピーク、計測可能な確保量 | CPU 候補数と GPU 可視数。プロセスメモリと GPU 資源使用量 |

最小の比較マトリクスは変更内容に応じて選ぶ。描画抽出なら無変更・1% 移動・全件移動・生成削除・初回、GPU 描画なら全可視・部分可視・画面外、1/複数ビュー・影・fallback。ストリーミングなら通常移動・境界往復・teleport・失敗からの回復。各ケースは検証対象であり、すべてに同じ時間目標を設ける必要はない。

数値検証の入口は [`FBZZTestBench --measure` と `Tools/BenchCompare.ps1`](benchmark-report.md)。物理や Math の単体比較、実 DX12 の描画、Playtest の機能・画質検証は別々に扱う。レポートには **対象区間と単位／前後の条件／P50・P95・P99 と標本数（取得できる場合）／出力の同等性／後退・未確認事項／元データ** を残す。BenchReport の ±3% 等の表示しきい値は同ツールの判定であり、全種類の計測の普遍的な有意差ではない。

## 過去の実測から言えること

以下は個別の計測結果。異なる時点・区間・機材の数値を足したり、現行作業ツリーの速度保証として使ったりしない。

| 比較 | 確認できた値 | 解釈の限界 |
|---|---|---|

## 追加最適化の判断条件

| 候補 | 着手の根拠 | 実装・採用前に確かめること |
|---|---|---|
| 静的 mesh を変更通知だけで差分抽出 | `GeometryBuild` が律速で、少数変更時の候補照合が支配的 | 全書き込み経路を追跡できるか。追跡不能な変更、親子、寿命世代、Undo、Shader Reload、Reset の代替経路を保てるか。候補全照合が残る間は O(K) と記載しない |
| 永続する材質準備・描画命令、PSO 事前準備 | command 組み立てか初回 PSO 作成が支配的 | 実行経路別に費用を分ける。PSO のメモリ内キャッシュ、シェーダーコンパイル、Driver の PSO 作成を区別し、初回の停止と保持メモリを測る |
| ジョブ基盤の改善 | CPU の実行時間より、投入・queue 待ち・batch 終了待ちがフレームを延ばしている | Phase、ComponentAccess、Scene の公開境界を維持できるか。背景タスクがある条件と無い条件で比較する |
| GPU 資源の物理エイリアス | 同時生存しない資源が多く、削減できる VRAM が確認できた | 寿命の診断値から共有可能 byte を見積もり、実 heap、資源状態、alias barrier と複数キューの依存を検証する |

詳細な不足項目と過去の判断は [最適化基盤の差分監査](engine-optimization-gap-audit.md) を参照する。採用後は対象経路の設計と計測記録を更新し、未計測の経路に結果を広げない。
