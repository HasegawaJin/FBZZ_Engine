# GPUキュー調査と画面外フレームのPresent削減

**画面外描画だけのフレームで不要だったPresentを省く変更を実装・採用した。** 主比較の1,000体はP50 0.9343 → 0.8214 ms、P99 1.3494 → 1.1635 ms。独立再測定でも短縮した。ただし効果は `SetRenderWhenOccluded(true)` を明示した画面外描画経路のもの。今回の「全件可視」はカメラのfrustum内という意味で、非表示ウィンドウのRenderTargetへ描画する。通常の画面表示のPresentスパイクが解決したという結果ではない。1万体の全フレームP99には悪化が残り、全条件のtail改善は達成していない。

## 原因を絞れた範囲

既存のCPU時刻と同じQPCに、nativeのGPU送信・Present・実Fence待機区間を対応させる任意のFrameTimeline記録を共通計測exeへ追加した。正式な比較では記録を停止する。管理者の名前付きWPRセッションだけを開始・終了し、他の記録には触れていない。

最初の完全GPU記録TraceV3は24,416,776イベント、最後のTraceV6は17,442,329イベント。ともにイベント/バッファ欠落0。DxgKrnl、DXGI、Direct3D12をTDHの実スキーマでデコードした。HAGSのハードウェアキューはContext作成とHwQueue作成・破棄のhandleと寿命で所有を照合した。旧QueuePacketのcontextだけではHAGSの仕事を拾えず、件数0をGPUの無負荷とは解釈していない。[取得状態・原本パス・SHA256](TraceEvidence.json)、[最終スキーマ](Full-GpuSchemas.json.gz)。

TraceV3の1,800計測フレームすべてで、描画送信区間にDirect3D12 ExecuteCommandList開始が1回、その後のPresent区間に同じcommand queueへの開始がもう1回あった。DXGI側もSyncInterval=0、ALLOW_TEARING、戻り値S_OKであり、非表示ウィンドウでも表示処理を通っていた。最大Present区間は1.4844ms。この仕事は画面外RenderTargetの成果物の生成・読戻しには不要だった。

TraceV6でも変更前600フレームはruntime送信1,200回、変更後の画面外600フレームは600回。各フレーム本来の描画送信は1回のまま。プロセス寿命内の所有ハードウェアキューのDMAイベント450/451は変更前それぞれ10,917、画面外だけの変更後それぞれ3,669へ減った。初期化・warmup・終了処理も含む件数で、GPU実行時間や厳密なqueue滞留時間ではない。[ハードウェアキューの記録](Full-QueueFacts.json)、[フレーム単位の照合](Full-PresentationPolicy.json)。

## BeginFrameの待機

変更前のTraceV3と軽いTraceV4の計3,600計測フレームでは、`WaitForFence` は完了済みとして戻り、実待機区間は0件。前回観測した3.7562msのblocked区間は再現せず、今回の根拠からその原因まで断定しない。

軽いruntime記録TraceV5では、CPU側の処理を短縮した画面外候補に実Fence待機が7件、最大0.4911ms出た。待機対象の実Fence値とフレームをnative scopeで記録しており、このケースのBeginFrame増加にはフレームスロットのGPU完了待ちが含まれる。必要な待機を取り除いたり、完了値を偽って資源を再利用したりしていない。詳しいGPU記録TraceV6では全4ケースで実待機0件で、記録負荷の違う実行同士を同一事象として結び付けない。通常モードではPresent最大1.1476msが残った。[待機と大きいBeginFrameの内訳](WaitFacts.json)、[詳しいnative時系列](Full-Chronology.json.gz)、[軽い記録のnative時系列](Validation-Chronology.json.gz)。

GPU飽和、他プロセスとの競合、割込み、ベンダー内部同期を各Present遅延の最終原因として特定できたわけではない。公開されていない新しいDirect3D12 Queueイベントの一部はこのOSのTDHで解決できず、offsetやGPU時間を推測していない。取得したETLは保存した。[Microsoft GPUView](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/using-gpuview)、[Presentの表示・同期契約](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiswapchain-present)。

## 実装と表示を維持する条件

DX12Contextにフレーム内のバックバッファ使用を持たせた。画面外継続を明示しており、バックバッファのClear・ClearDepth・Drawがなく、外部記録の通知もないときだけPresentを省く。RenderTargetをバックバッファへ再束縛するだけでは使用扱いにしない。ImGui/IblBaker等の外部記録は既存のパイプライン状態変更通知で保守的に使用扱いにする。

EndFrameのClose、ExecuteCommandLists、実FenceのSignal、frame slot更新は省略しない。BeginFrameの再利用待機、資源退役、GPU queryの回収、描画内容・件数も維持した。通常モードは毎フレームPresentし、画面外継続モードでもバックバッファを更新したフレームはPresentする。変更はprivate実装3ファイル。公開IRenderer API、native入力1,358件のmembership、6 DLLのexport名/ordinalは維持した。比較DLLはGraphicsだけ異なり、他5 DLLと前後の計測exeはbyte同一。[この作業だけの差分](TaskDelta.patch)、[最終ABI・入力監査](VerifiedConfirm-ArtifactAudit.json)、[設計](../../design/graphics-library.md)。

TraceV6の600計測フレームごとの実測は次のとおり。全2,400フレームをnative時刻とDXGI/D3D12に照合し、期待回数と画像hashの一致をassertした。

| 動作 | Present回数 | runtime Execute開始 | 本来の描画送信フレーム |
|---|---:|---:|---:|
| 変更前・画面外だけ | 600 | 1,200 | 600 |
| 変更後・画面外だけ | 0 | 600 | 600 |
| 変更後・7フレームごとにバックバッファClear | 86 | 686 | 600 |
| 変更後・通常モード | 600 | 1,200 | 600 |

custom WPR profileのTraceV4/V5にはDxgKrnlが入らず、ハードウェアキューの証拠には使わなかった。また初回の通常モード制御は既存の正数用設定readerが0を既定値へ戻す問題で有効になっておらず、検証assertで検出した。専用の無効化設定とconfigログを追加し、TraceV6で取り直して600回を検証した。失敗した取得も保存した。通常表示やImGuiの実画面での長時間playtestは今回実施していない。

## 前回と同条件の正式比較

ユーザー承認済みの既存FBZZ環境、Release LTO、i7-14700F / RTX4070、DX12、1920×1080、Forward Unlit。instancing・shadow・VSync無効。affinity240（4論理CPU）、High priority、HighQoS検証済み。ABBAABで各版3プロセス、1,000体は600 warmup、他は120 warmup、その後各600標本。Profiler・ETW・FrameTimeline・thread cycle計測は停止し、読戻し・ログは計測外。前後同じexe・shader、DLLだけを隔離した。CPU経過時間は変更適用、WaitForCpuFrame、BeginFrame、RenderSystem、EndFrameを含む。P50は3プロセスのP50の中央値、P95/P99は各1,800標本を結合した分位点。単位ms、前 / 後、負の変化は短縮。[環境](First-gpu-Environment.json)、[全分布集計](First-gpu-Summary.json)。

## 正しさ・ビルド・成果物

AgentBuildで変更C++のコンパイル、既存Release LTOでGraphicsとnative計測・描画suiteをビルドした。コンパイル/リンクエラー0。既存のMSB8028中間ディレクトリ共有警告がある。最終コードのコメント形式と入力mapのhash、全export ordinalを確認した。

実DX12描画・読戻しsuiteは230合格＋既存disabled3、Graphics CPU304合格、Skinning58合格、計592合格。すべて最終候補と同じGraphics DLL hashの隔離runtimeで実行した。既存suiteの内容は拡張後の全件であり、前回の選択53件だけではない。[native描画](NativeGraphics.json)、[Graphics CPU](GraphicsCpu.json)、[Skinning](Skinning.json)、[実行物の一致](TraceEvidence.json)。

一回限りの取得・計測・解析コードとETL原本は `Scratch/GpuQueue20261023/` に保存した。継続調査には通常表示でのPresent内部の滞留と、1万体RenderSystem側のP99変動が残る。スケジューリングやドライバー設定を変更していない。
